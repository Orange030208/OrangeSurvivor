# 项目异味报告

生成时间: 2026-05-14 06:10:04 +08:00
审计原则: 以当前源码实际行为为准，不沿用历史审计结论。
审计范围: `Assets/Scripts` 核心运行时代码、Manager/Service/Controller、输入/设置链路、内容池链路、UI 框架核心。

## 总体结论

当前项目技术债等级为 **中高**。短期继续迭代可行，但武器、游戏流程、UI 框架、商店、奖励选择和波次这些核心链路集中在大类中，且大量依赖全局静态入口和场景查找。后续继续添加武器、商店规则、奖励规则、UI 页面和输入平台时，回归风险会快速增加。

本轮相比上轮的关键变化是：当前内容池运行时代码已经主要使用 `ContentHistoryState`，但历史状态的持有方式仍分散在业务模块中；输入系统已经引入 `InputModuleRuntime`，但设置 UI 和设置服务仍直接依赖 `GameInput.Instance`。

## 异味类型归纳

- **God Object**: `Weapon`, `UIManager`, `GameManager`, `SettingsPanelManager` 最明显。
- **过度耦合 / 跨层调用**: `GameManager` 直接驱动 UI、地图、波次、玩家、音频；`SettingsPanelManager` 直接调用输入、显示、音频、UI Modal。
- **隐式依赖**: `FindFirstObjectByType`、`GameInput.Instance`、`UIManager.Instance`、`GameContentRuntime.Provider`、`RunProgressionRuntime.CurrentSnapshot`。
- **状态混乱风险**: `RewardSelectionManager` 的异步队列/暂停/弹窗状态，`GameManager` 的 `stateTransitionVersion` / `isWaveEndFlowRunning` / `isEnteringPostWaveStateAfterCleanup`。
- **Update/Tick 热点**: `WaveManager.Update`、`UIManager.Update` 合理存在，但都承载了跨职责调度。
- **运行时动态补组件**: `UIManager` 在运行时创建/补齐 Canvas、Raycaster、Button 等框架组件；对框架可接受，但需要清楚边界，避免业务层模仿。

## 优先修复顺序

1. P0: 先拆 `Weapon` 和 `GameManager` 的高频变更职责，避免玩法迭代继续压到两个大类里。
2. P1: 给 `GameEventBus` 增加自动清理和生命周期约束。
3. P1: 把商店、奖励选择的内容抽取/应用/视图状态拆成可测试服务。
4. P2: 逐步把输入和设置从静态全局入口改成显式依赖。
5. P2: 属性系统默认值和 modifier source 类型化。
