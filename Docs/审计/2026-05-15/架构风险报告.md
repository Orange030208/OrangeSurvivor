审计范围: 项目结构、模块边界、运行时全局状态、核心业务调用链、SOLID 风险、可维护性和扩展性。

## 架构健康结论

项目仍能支撑短期玩法迭代，但中长期迭代风险已经偏高。风险来源主要是:
- 目录模块化没有编译边界支撑，属于伪模块化。
- 核心流程由少数 Manager 和 God Object 串联。
- 静态入口和场景查找仍较多，依赖来源不透明。
- 内容池迁移已进入可用状态，但历史生命周期没有统一定版。
- 文档与当前实现存在术语和类名漂移。

## SOLID 与职责边界

| 原则 | 当前风险 | 具体位置 |
| --- | --- | --- |
| SRP | 多个类承担多个职责 | `Weapon`, `UIManager`, `GameManager`, `ShopManager`, `RewardSelectionManager`, `SettingsPanelManager` |
| OCP | 新玩法类型容易修改核心类 | 新武器攻击模式改 `Weapon`，新商店物品类型改 `ShopManager`，新奖励流程改 `RewardSelectionManager` |
| DIP | 高层流程依赖静态入口和具体 MonoBehaviour | `GameContentRuntime.Provider`, `RunProgressionRuntime.CurrentSnapshot`, `GameInput.Instance`, `UIManager.Instance` |
| ISP | 部分上下文对象承载过多依赖 | `RewardSelectionHandlerContext`, `ShopPageContext`, `GamingPageContext` |
| LSP | 未发现严重继承替换问题，但 `Entity` / `EntityComponentBase` 组合契约依赖运行时装配 | `Player`, `Enemy`, `Weapon`, `AttributeManager` |

## 模块危险度排序

1. `Weapon` / 武器运行时: 高频改动、职责最多、玩法影响最大。
2. `GameManager` / 主流程: 状态、UI、暂停、场景装配集中。
3. `UIManager` / UI 框架核心: 体量最大，影响所有 UI。
4. 内容池历史链路: 文档与实现不一致，影响商店、奖励、掉落、刷怪。
5. `ShopManager` / `RewardSelectionManager`: 经济与奖励流程交织 UI 和业务。
6. `GameEventBus`: 全局状态清理风险。
7. `SettingsPanelManager` / 输入设置: 平台裁剪和输入重绑扩展风险。

## 可维护性评估

| 维度 | 等级 | 说明 |
| --- | --- | --- |
| 技术债 | 中高 | 运行时代码可编译，测试基础存在，但核心类过大且边界弱。 |
| 可维护性 | 中 | 局部代码命名和校验有所改善，但高频流程仍集中在 Manager。 |
| 可扩展性 | 中 | 内容池、推进、UI 框架已有抽象，但生命周期和职责归属未完全定版。 |
| 新人接手成本 | 高 | 缺根 README，文档存在旧术语和不存在类名，入口分散。 |
| 重构风险 | 中高 | 核心流程耦合深，必须小步拆分并保持序列化字段稳定。 |

## 最值得先重构的部分

首选 `Weapon` 与 `GameManager`。原因:
- 二者都是高频修改文件，近期 git 记录显示 `Weapon.cs`、`GameManager.cs` 持续变化。
- 二者分别覆盖玩法手感和主流程，出错影响面最大。
- 二者可以通过“保持 MonoBehaviour 门面，抽可测试服务”的方式低风险拆分。

紧随其后是内容历史生命周期定版。否则商店、奖励、掉落、刷怪和随机武器奖励会继续在多个历史源之间扩散。
