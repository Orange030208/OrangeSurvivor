## 阶段 5: 内容历史生命周期定版

### 当前事实

- `ShopManager` 持有实例级 `ContentHistoryState`。
- `RewardSelectionManager` 持有实例级 `ContentHistoryState`。
- `DropManager` 持有实例级 `ContentHistoryState`。
- `WaveSpawnExecutor` 持有实例级 `ContentHistoryState`。
- `AddRandomWeaponCard` 持有静态 `ContentHistoryState`，并在 `SubsystemRegistration` reset。

### 推荐方案

建立 `RunContentHistory`:
- 由局内 Run/Session Bootstrap 创建。
- 内部持有一个 `ContentHistoryState`。
- 业务通过 `ContentRollContext` 接收同一个历史对象。
- `ContentHistoryScope` 继续用 `scopeId + poolId + ownerId` 隔离不同业务池。

### 验证

- `ContentPoolTests`
- `RewardSelectionTests`
- 新增测试覆盖商店、掉落、刷怪、随机武器奖励的历史隔离和共享规则。

## 阶段 6: 商店与奖励选择服务化

### 商店

| 服务 | 职责 |
| --- | --- |
| `ShopRollService` | 根据 pool、刷新次数、锁定物品生成候选商品。 |
| `ShopPurchaseService` | 根据当前玩家和商品执行购买，返回成功/失败结果。 |
| `ShopState` | 维护当前商品、锁定、刷新成本、免费刷新次数。 |

完成标准:
- `ProcessAccessoryPurchase` / `ProcessWeaponPurchase` 不再全场景查找组件。
- UI 只订阅 `ShopViewState`。
- 购买失败原因仍可定位。

### 奖励选择

| 服务 | 职责 |
| --- | --- |
| `RewardSelectionFlow` | 队列、当前请求、取消、结果等待。 |
| `RewardPauseScope` | 暂停申请和释放成对处理。 |
| `RewardApplicationService` | 应用升级卡、宝箱、武器等奖励。 |

完成标准:
- `RewardSelectionManager` 不直接维护所有异步状态。
- 连续升级、弹窗取消、GameState 退出路径有测试。

## 阶段 8: asmdef 落地

### 推荐顺序

1. 拆 `Assets/Scripts/*/Editor` 到 Editor asmdef。
2. 拆 `Assets/Tests/Editor` 到 Test asmdef。
3. 拆 `OrangeUIFramework` 独立 Runtime asmdef。
4. 拆 `Content.Runtime` 与 `Content.Editor`。
5. 拆 `Combat`、`Pooling`、`RunProgression` 等低耦合纯逻辑模块。
6. 最后处理 `Managers` 和业务 UI，因为它们当前耦合最深。

### 验证

- Unity 编译通过。
- `dotnet build Assembly-CSharp.csproj -nologo -clp:ErrorsOnly` 或对应新 csproj 构建通过。
- 现有 EditMode 测试通过。

## 最推荐下一步

先执行阶段 1 和阶段 2。原因是这两步成本低、风险小、收益高:

1. 文档旧术语会持续误导后续重构，先修掉可以减少返工。
2. `GameEventBus` 自动 reset 是小改动，但能直接降低跨场景和关闭 Domain Reload 的隐性风险。

随后再进入 `Weapon` 和 `GameManager` 的拆分，避免在文档和全局生命周期仍不清晰时启动高风险重构。
