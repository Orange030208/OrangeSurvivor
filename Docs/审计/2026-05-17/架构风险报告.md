# 架构风险报告

生成时间: 2026-05-17 06:08:52 +08:00

项目层级判断: 长期迭代型小型 Unity 游戏项目。短期继续做玩法内容可行，但核心流程的维护成本已经偏高，后续迭代需要先压缩全局状态、巨型类和数据导入风险。

## 技术基线

- Unity 版本: `2022.3.62f3c1`
- 渲染管线: URP `14.0.12`
- 主要依赖: UniTask、NaughtyAttributes、Input System、TextMeshPro、UGUI、DOTween、Behavior Designer、Unity Test Framework、UnitySkills/MCP
- 目录信号: 运行时代码集中在 `Assets/Scripts`，内容资产集中在 `Assets/GameContent`
- asmdef: 本轮未发现项目自有 `.asmdef`，仍主要依赖默认 `Assembly-CSharp` / `Assembly-CSharp-Editor`
- 测试: `Assets/Tests/Editor` 覆盖武器、波次、内容池、奖励、设置、运行推进、屏幕震动等局部规则

## SOLID 与模块边界判断

- SRP 风险最高: `Weapon`、`UIManager`、`GameManager`、`SettingsPanelManager`、`ShopManager`、`RewardSelectionManager`。
- DIP 风险明显: `GameEventBus`、`GameInput.Instance`、`UIManager.Instance`、`AudioManager.Instance`、`GameContentRuntime.Provider`、`RunProgressionRuntime.CurrentSnapshot`。
- OCP 风险集中在数据导入: JSON 字段和支持的 Feature 类型通过 switch/字符串控制，新增 Feature 需要改导入器。
- 伪模块化存在: 目录分层存在，但无 asmdef 和依赖方向约束。
- 数据流最不透明区域: `GameEventBus` 驱动的 GameManager/WaveManager/RewardSelectionManager/ShopManager 交互，以及 ContentHistoryState 分散持有。

## 当前架构是否还能支撑后续迭代

可以支撑短期内容迭代，但不建议继续在当前结构上直接叠加大量新玩法。最需要先处理的是两类低成本高收益问题:

1. 生命周期污染: `GameEventBus` reset、全局输入/内容/推进入口的使用边界。
2. 数据资产安全: JSON 导入删除行为、文档中旧术语、内容历史生命周期说明。

在这两类处理前，直接启动 `Weapon` / `UIManager` / `GameManager` 的大拆分风险偏高。
