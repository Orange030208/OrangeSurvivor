# 架构风险报告

生成时间: 2026-05-13 06:09:11 +08:00

审计范围: Unity 项目基线、`Assets/Scripts` 架构边界、运行时数据流、核心 Manager、内容池、UI 框架

## 技术基线

- Unity: 2022.3.62f3c1
- 渲染管线: URP 14.0.12
- 主要包: Input System 1.7.0、UniTask、本地 NaughtyAttributes、DOTween、Behavior Designer、Unity MCP / Unity Skills
- 程序集边界: 当前 `rg --files -g "*.asmdef"` 无结果，所有运行时代码基本落在默认程序集。
- 目录信号: 代码按 `Weapons`、`Managers`、`Content`、`Waves`、`OrangeUIFramework`、`UI`、`Enemy` 等目录组织，但编译与依赖层面没有强边界。

## 项目健康度

| 维度 | 评级 | 说明 |
|---|---|---|
| 技术债等级 | 中高 | 真实崩溃点比上轮少，但结构性债务集中在核心流程和内容迁移。 |
| 可维护性 | 中 | 局部模块如 Combat、Pooling、部分 Content 类型有明确抽象，但主流程类过大。 |
| 可扩展性 | 中 | 新玩法能继续接，但会持续压到 `Weapon`、`GameManager`、`ShopManager`、`RewardSelectionManager`。 |
| 新人接手成本 | 高 | 缺 README、缺场景装配契约、无程序集边界，文档又混有目标方案和当前实现。 |
| 重构风险 | 高 | `Weapon`、`UIManager`、`GameManager` 触达面大，必须分阶段切片。 |
| 潜在崩溃点 | 中 | 明确空引用 P0 已减少，但全局 Provider、场景依赖、异步 UI 流程仍是风险点。 |

## 当前架构能否支撑后续迭代

可以支撑短期功能迭代，但不适合继续在当前结构上长期堆主流程。项目已经进入“玩法系统可跑、核心类过载、文档滞后”的阶段。下一阶段最重要的不是引入大框架，而是把核心运行时依赖显式化，并把高频变化的规则从 MonoBehaviour 中切出去。

## 优先修复顺序

1. 内容抽取系统迁移状态定版：解决 `ContentHistoryState`、`ContentPoolRuntimeState`、`UpgradeRunState` 的并存关系。
2. 建立场景装配契约：明确 Bootstrap、输入、UI、GameManager、WaveManager 的必需引用。
3. 拆 `GameManager` 状态流：优先抽 UI 路由和暂停控制。
4. 拆 `ShopManager` / `RewardSelectionManager`：先抽纯服务，降低玩法迭代回归面。
5. 拆 `Weapon`：围绕运行时属性、投射物、命中窗口分层。
6. 开始 asmdef：从低耦合框架/纯逻辑模块开始，不要先拆最复杂的 Gameplay。
